# Minecraft-агент: план реализации

**Версия:** 1.2  
**Статус:** рабочий план к исполнению  
**Источник требований:** приложенное целевое ТЗ «Minecraft-тело для ИИ-агента»

---

## 1. Цель и результат

Построить управляемого Minecraft-персонажа для ИИ-агента на базе настоящего Java Edition клиента с Fabric-модом.

Первая рабочая версия должна:

- подключаться к выбранному тестовому серверу под выделенным аккаунтом;
- наблюдать состояние мира и передавать его управляющему сервису;
- выполнять базовые игровые действия штатными клиентскими механизмами;
- принимать поручения от владельца и уполномоченных игроков;
- поддерживать экономичный режим без постоянной отрисовки;
- включать изображение и ручное управление в той же игровой сессии;
- гарантированно останавливать автоматические действия при перехвате;
- сохранять задачи, память и настройки между перезапусками.
- давать полный веб-дашборд для настройки серверов, версий клиента, мозга, прав, лимитов, рендера и поведения;
- работать в двух режимах: со встроенным собственным агентом и с подключаемым внешним агентом;
- запускаться на Linux-сервере без физического монитора и графического рабочего стола.

Ключевой приоритет: **надёжная игра и управление**, затем единая личность и память, затем серверные сценарии, и только после этого оптимизация.

## 2. Технологические решения и переносимость

| Компонент | Решение первой версии |
|---|---|
| Клиент | Minecraft Java Edition, настоящий клиент |
| Мод-загрузчик | Fabric |
| Язык мода | Java 21 |
| Точка внедрения | Fabric API и точечные Mixin |
| Версия Minecraft | Настраивается в профиле клиента; 1.21.1 используется только как первый тестовый профиль |
| Управляющий сервис | Node.js 22 LTS, TypeScript |
| HTTP API | Fastify |
| Транспорт мода и сервиса | WebSocket для локального режима и исходящий WSS/TLS для удалённого режима |
| Валидация | Zod |
| База данных | SQLite, миграции через Prisma |
| Панель | Vite + React + TypeScript |
| Видео | Сначала проверка снимков и простого потока, затем WebRTC, если прототип подтвердит целесообразность |
| Навигация | Baritone как кандидат; при несовместимости реализуем ограниченный локальный планировщик |
| Тесты | Gradle/JUnit для мода, Vitest для сервиса, Playwright для панели |
| Основное развёртывание | Linux + Docker Compose: клиент, сервис, панель, reverse proxy, тома состояния |
| Графика на Linux VPS | Виртуальный дисплей и программный OpenGL, без физического монитора и рабочего стола |
| Переносимость | Сервис и панель работают на Linux, macOS и Windows; клиент запускается через контейнер или нативный runner профиля |
| Аутентификация | Профиль `MICROSOFT` для обычных серверов и профиль `OFFLINE_SERVER` для offline/cracked-серверов |

Сервер, версия Minecraft, Fabric, Java-рантайм, моды, рендер, лимиты, мозг и модель не зашиваются в код. Все они описываются конфигурационными профилями и редактируются в дашборде.

Каждый профиль сервера и клиента фиксирует свою комбинацию версий. Это позволяет поддерживать несколько окружений без превращения системы в неразбериху «на все версии сразу»: в один момент активен один сервер и один клиентский профиль, но профилей может быть сколько угодно.

### Headless Linux

Сервер без графического интерфейса подходит.

Для настоящего Minecraft-клиента всё равно нужен графический контекст, поэтому на Linux VPS используется виртуальный дисплей, например `Xvfb`, и OpenGL-стек, например Mesa/llvmpipe. Монитор, клавиатура, мышь и рабочий стол пользователю не нужны.

Дашборд открывается в обычном браузере владельца и управляет серверным процессом по сети. В экономичном режиме постоянное кодирование видео и рендер выключены; изображение включается только для наблюдения, проверки входа или ручного управления.

Если целевой VPS не тянет программный рендер или требует слишком много ресурсов, это становится ограничением конкретного профиля, а не причиной переписывать архитектуру.

### Переносимость и энергопотребление

Ядро системы делается переносимым:

- управляющий сервис и дашборд работают на Linux, macOS и Windows;
- Fabric-мод использует Java и не зависит от конкретной ОС;
- на Linux основной способ запуска — контейнер с виртуальным дисплеем;
- на настольных системах можно использовать нативный клиент без Docker;
- совместимость конкретной архитектуры CPU и версии клиента проверяется профилем.

Энергопотребление снижается не одним флагом, а набором режимов:

- `OFFLINE`: клиент остановлен, сервис продолжает принимать настройки и задачи;
- `ECONOMY`: клиент работает, рендер и кодирование видео отключены;
- `OBSERVE`: низкое разрешение и низкий FPS только для наблюдения;
- `INTERACTIVE`: полноценное изображение и ручное управление;
- события передаются по значимости, а полные снапшоты не опрашиваются постоянно;
- LLM вызывается по событиям и контрольным интервалам, а не каждый игровой тик;
- Docker-профили ограничивают CPU и RAM;
- автоматический перезапуск и повторный вход ограничены, чтобы сбой не съедал ресурсы.

Числовые лимиты FPS, снапшотов, вызовов модели, CPU и RAM настраиваются в дашборде и фиксируются только после замеров на целевом окружении.

### Offline и cracked-серверы

Поддерживаются два типа подключения:

1. `MICROSOFT`: сервер проверяет Mojang/Microsoft-аккаунт.
2. `OFFLINE_SERVER`: сервер работает в offline-режиме и принимает подключение с настраиваемым игровым ником.

Для `OFFLINE_SERVER` действуют жесткие границы:

- используется клиент и файлы игры, предоставленные пользователем в рамках лицензионных требований;
- система не скачивает и не распространяет пиратский клиент;
- система не обходит Microsoft-аутентификацию и не модифицирует защиту лицензии;
- nick на offline-сервере не считается доказательством личности;
- административные права и поручения подтверждаются через дашборд или доверенный внешний канал;
- при подозрении на подмену ника система не повышает права и запрашивает подтверждение.

Серверные плагины вроде `AuthMe` поддерживаются через тот же механизм `/login`, но их пароли также хранятся в секретах и не попадают в память, промпт и логи.

### Онбординг и топологии подключения

После установки дашборд запускает мастер первоначальной настройки. Система не требует заранее править файлы вручную: мастер создаёт профили в базе, а позже все значения можно изменить в обычных экранах настроек.

Шаги онбординга:

1. Создание учетной записи владельца и защита дашборда.
2. Выбор топологии: всё на VPS, клиент на домашнем компьютере, сервис на VPS, или гибрид.
3. Подключение клиентского мода через pairing-код.
4. Выбор типа входа: `MICROSOFT` или `OFFLINE_SERVER`.
5. Для `OFFLINE_SERVER`: указание сервера, ника и, при необходимости, серверного пароля входа.
6. Настройка профиля клиента: версия Minecraft, Fabric, Java, моды, рендер.
7. Настройка профиля сервера: адрес, лобби, плагины, лимиты.
8. Выбор режима мозга: `BUILT_IN` или `EXTERNAL`.
9. Настройка модели, бюджета и таймаутов, если выбран встроенный мозг.
10. Настройка прав, базовых запретов и режима присутствия.
11. Проверка соединения, совместимости, секретов и завершение установки.

Топологии подключения:

- `LOCAL`: сервис, клиент и дашборд работают на одной машине; используется локальный WebSocket или Unix socket.
- `REMOTE_CLIENT`: настоящий Minecraft с Fabric-модом запущен на домашнем компьютере, а управляющий сервис, дашборд и мозг работают на VPS.
- `REMOTE_PLUGIN`: опциональный серверный плагин подключается к сервису для доверенного сервера и предоставляет дополнительные события, идентификацию или процедуры.

В дашборде можно переключать активную топологию между `LOCAL` и `REMOTE_CLIENT`. Это не отдельные установки и не потеря данных: сохраняются профили сервера и клиента, задачи, память, права и ограничения.

Переключение топологии:

1. Открыть экран `Deployment`.
2. Выбрать `LOCAL` или `REMOTE_CLIENT`.
3. Указать активный client runner или endpoint мода.
4. Проверить pairing, TLS и heartbeat.
5. Перезапустить активную игровую сессию.
6. Подтвердить, что новый компонент подключился и получил свежий снапшот.

В режиме `REMOTE_CLIENT` мод сам устанавливает исходящее защищённое WebSocket-соединение к сервису на VPS. Пробрасывать порты на домашнем компьютере не нужно. В настройках мода указываются endpoint сервиса и pairing-код; после подтверждения выдается постоянный токен клиента.

Такая топология экономит ресурсы VPS: рендер и Minecraft работают на домашней машине, можно использовать её GPU, а на VPS остаются сервис, мозг, память и дашборд. Если включается наблюдение или ручное управление, кадры передаются через сервис в браузер владельца.

Опциональный серверный плагин не обязателен для работы агента. Он только расширяет наблюдение и подтверждение личности на серверах, которыми управляет владелец или где администрация явно разрешает интеграцию. Плагин не получает права над агентом автоматически и не может обходить лимиты.

Общие настройки подключения мода и плагина:

- endpoint управляющего сервиса;
- режим TLS;
- pairing-код или постоянный токен;
- имя окружения;
- разрешенные версии протокола;
- интервал heartbeat;
- таймауты и политика переподключения;
- уровень логирования и диагностика без секретов.

Настройки в клиентском моде:

- endpoint управляющего сервиса;
- pairing-код или токен клиента;
- проверка TLS-сертификата;
- автоподключение и политика повторов;
- локальный экран состояния соединения;
- режим логирования без секретов;
- выбранные профили, полученные от сервиса после pairing.

Настройки в опциональном серверном плагине:

- endpoint управляющего сервиса;
- pairing-код или токен интеграции;
- идентификатор сервера и версия плагина;
- список передаваемых событий;
- heartbeat и таймауты;
- ограничение действий только теми, что разрешены в дашборде.

Игровой ник для `OFFLINE_SERVER` и серверные пароли настраиваются в дашборде, а не в config-файле мода или плагина. Секреты остаются в защищенном хранилище сервиса.

Дашборд показывает состояние каждого подключенного компонента: мод, плагин, клиент, сервис, внешний мозг, задержку канала и последнюю ошибку.

### Режимы агентной системы

Система поддерживает два издания на одной игровой базе:

1. **Built-in Agent Edition.** В комплекте собственный агент: системный промпт, память, планировщик, модель и ограничения настраиваются в дашборде.
2. **External Agent Edition.** Встроенный мозг отключается, а игровое тело подключается к внешнему агенту: `teleton-agent`, другая агентная платформа или пользовательская реализация через открытый контракт.

Оба режима используют одинаковые API, события, задачи, навыки и правила безопасности. Меняется только источник намерений.

## 3. Границы первой версии

### Входит

- Один аккаунт и одно активное подключение одновременно.
- Несколько профилей серверов и клиентов, управляемых из дашборда.
- Онбординг после установки и все основные настройки через дашборд.
- Режимы подключения `LOCAL`, `REMOTE_CLIENT` и `REMOTE_PLUGIN`.
- Профили аутентификации `MICROSOFT` и `OFFLINE_SERVER`.
- Настраиваемые версии Minecraft, Fabric, Java, модов и графических профилей.
- Встроенный агент и подключаемый внешний агент через единый контракт.
- Адаптер `teleton-agent`, добавляемый после аудита его фактических API.
- Базовые навыки: движение, добыча, крафт, печь, инвентарь, еда, контейнеры, возврат домой, простые постройки.
- Полноценный дашборд: мониторинг, конфигурация, задачи, права, память, рендер и ручное управление.
- SQLite-память: задачи, события, места, проекты, правила, подтвержденные процедуры.
- Механизмы безопасности: права, лимиты, запреты, `control_epoch`, секреты, аудит.
- Headless-запуск на Linux и портируемый сервис/панель.

### Не входит

- Поддержка всех версий Minecraft.
- NeoForge и другие загрузчики.
- Гарантия, что любой профиль клиента заработает без проверки совместимости.
- Скачивание, распространение или взлом пиратского клиента.
- Полноценный PvP-бот.
- Произвольные капчи и автоматическое прохождение любых проверок.
- Универсальная поддержка всех плагинов.
- Обязательный серверный плагин для работы агента.
- Параллельное управление несколькими персонажами.
- Сложные редстоун-механизмы и большие автоматические стройки.

## 4. Целевая архитектура

```text
┌───────────────────────────────┐
│ Built-in агент / внешний мозг │
│ личность, память, намерения   │
└───────────────┬───────────────┘
                │ единый контракт мозга
┌───────────────▼───────────────┐
│ Управляющий сервис             │
│ сессии, права, задачи, навыки  │
└───────────────┬───────────────┘
                │ WS/WSS: LOCAL или REMOTE_CLIENT
┌───────────────▼───────────────┐
│ Fabric-мод в настоящем клиенте │
│ ввод, наблюдение, рендер       │
└───────────────────────────────┘

┌───────────────────────────────┐
│ Веб-дашборд                    │
│ профили, права, мониторинг     │
└───────────────────────────────┘

┌───────────────────────────────┐
│ Опциональный серверный плагин │
│ события, identity, процедуры  │
└───────────────────────────────┘
```

Обязательные свойства:

- Сервис работает при выключенном клиенте и принимает настройки и поручения.
- Мод не является личностью и не принимает высокоуровневых решений.
- Действия выполняются через штатные клиентские механизмы.
- Никаких прямых телепортов, подмены физики и взаимодействий вне доступной дистанции.
- Игровой чат, книги, таблички и интерфейсы не являются системными инструкциями.
- Защищенные действия проверяются централизованно, независимо от источника команды.
- Активен только один высокоуровневый мозг: встроенный или внешний.

### 4.1. Дашборд и конфигурация

После установки первым открывается онбординг-мастер. Он проводит владельца через создание учетной записи, топологию, pairing мода или плагина, выбор аутентификации, клиентский и серверный профили, режим мозга, лимиты и финальную проверку. Мастер можно пройти заново без потери задач и памяти.

Основные экраны дашборда:

- `Onboarding`: пошаговая первичная настройка и проверка готовности;
- `Deployment`: выбор и переключение топологии `LOCAL` / `REMOTE_CLIENT`;
- `Connections`: состояние мода, опционального плагина и внешнего мозга;
- `Profiles`: серверы, клиенты, версии, Java, Fabric и моды;
- `Identity`: Microsoft-аккаунт или offline-профиль с ником;
- `Rules`: промпт, права, запреты и лимиты;
- `Sessions`: процесс, соединение, присутствие и рендер;
- `Tasks`: очередь, история и результаты;
- `Memory`: места, проекты, обещания и процедуры серверов;
- `Diagnostics`: логи, ресурсы, задержки и безопасный экспорт.

Дашборд редактирует:

- профили серверов: адрес, порт, версию, правила, логин, лобби, плагины, лимиты;
- аутентификацию: Microsoft-аккаунт или offline-профиль с ником;
- профили клиента: версию Minecraft, Fabric, Java, моды, JVM-флаги, разрешение, рендер;
- режим мозга: встроенный агент или внешний endpoint;
- модель и бюджет: провайдер, модель, лимиты вызовов, стоимость, таймауты;
- промпт и правила: личность, обязанности, запреты, временные указания;
- права: владельцы, администраторы, доверенные игроки, подтверждение личности;
- задачи и приоритеты;
- торговлю: лимиты, защищенные предметы, минимальный остаток, подтверждения;
- память: места, проекты, обещания, процедуры серверов;
- графику: `ECONOMY`, `OBSERVE`, `INTERACTIVE`, FPS, разрешение, звук;
- присутствие: `AUTO`, `ALWAYS_ONLINE`, `FORCED_OFFLINE`, расписание;
- ресурсы: ограничения CPU/RAM, частота снапшотов, уровни логирования.

В экране `Connections` можно:

- создать pairing-код для мода или плагина;
- посмотреть endpoint для удалённого подключения;
- отозвать токен конкретного устройства;
- включить или выключить TLS;
- увидеть heartbeat, задержку, версию протокола и причину последнего разрыва;
- переключить соединение между локальным и удалённым режимом.

Каждое изменение конфигурации:

- валидируется схемой;
- сохраняется с версией, автором и временем;
- попадает в аудит;
- может откатиться к предыдущей версии;
- вызывает перепроверку активной задачи, если влияет на права или ограничения.

Секреты хранятся отдельно от обычной конфигурации и не попадают в экспорт, снапшоты, промпт и логи.

### 4.2. Контракт внешнего мозга

Внешний агент подключается через открытый контракт, а не через приватные внутренние функции.

Контракт включает:

- поток событий и снапшотов;
- создание и обновление задач;
- запрос на запуск навыков;
- получение результатов и ошибок;
- чтение памяти в разрешенных границах;
- работу с ролями и лимитами;
- уведомление о необходимости человека.

Дашборд позволяет задать endpoint, тип транспорта, токен, таймауты и политику fallback. Если внешний мозг недоступен, ручное управление и административные команды продолжают работать.

## 9. Главные риски и решения

| Риск | Действие |
|---|---|
| Отключенный рендер ломает наблюдение | Сохранить больше графических ресурсов и уменьшить глубину оптимизации |
| Быстрое включение изображения нестабильно | Приоритет ручному управлению, а не максимальной экономии |
| WebRTC дорог на VPS | Использовать снимки или пониженное разрешение |
| Baritone несовместим | Реализовать ограниченную локальную навигацию |
| Нельзя достоверно определить автора чата | Не повышать права без доверенного подтверждения |
| Результат сделки неясен | Пометить `UNKNOWN`, сверить состояние, не повторять автоматически |
| `teleton-agent` отличается от ожиданий | Строить адаптер только по фактическим API |
| Сервер запрещает автоматизацию | Остановить работу на этом сервере |
| VPS без физической графики не запускает клиент | Использовать виртуальный дисплей и совместимый OpenGL-стек; при необходимости выбрать другой профиль или хост |
| Слишком много настроек вносит ошибки | Схемы, предпросмотр изменений, аудит, откат и профиль совместимости |
| Внешний мозг использует несовместимый контракт | Версионировать API и показывать явную ошибку совместимости |
| Ник на offline-сервере подделан | Не повышать права без подтверждения через дашборд или доверенный канал |
| Пользователь просит обойти защиту лицензии | Явно отклонить; поддерживается только offline-сервер с легальным клиентом пользователя |
| Домашний компьютер за NAT | Мод подключается исходящим WSS к VPS; пробрасывать порты не нужно |
| Утечка токена мода или плагина | Отозвать токен в дашборде, пересоздать pairing и проверить аудит |
| Потеря связи между модом и VPS | Сбросить автоматический ввод, остановить навык и безопасно переподключиться |

## 10. Определение готовности

Проект считается готовым к повседневному использованию, когда:

- пройдены все обязательные приёмочные сценарии;
- ручной перехват стабилен и не конфликтует с агентом;
- команды владельца работают без LLM;
- вход и восстановление не зацикливаются;
- задачи сохраняются и проверяют результат;
- права и лимиты нельзя обойти через чат или MCP;
- память работает в выбранном режиме;
- профили серверов, клиентов и мозга редактируются через дашборд;
- онбординг позволяет довести систему до первой сессии без ручных конфигов;
- поддерживаются локальная и удаленная топологии подключения мода;
- оба режима мозга проходят одинаковые ключевые сценарии;
- ресурсы измерены на целевом окружении;
- известные ограничения и проблемы задокументированы.

## 11. Первые практические шаги

1. Создать репозиторий и базовую структуру каталогов.
2. Оформить исходные требования и приёмочные сценарии.
3. Описать схему профилей сервера, клиента, мозга, аутентификации и графических режимов.
4. Описать онбординг и connector-протокол для `LOCAL`, `REMOTE_CLIENT`, `REMOTE_PLUGIN`.
5. Собрать минимальный Fabric-мод с WS/WSS-транспортом.
6. Реализовать сервисный каркас с состояниями, SQLite и конфигурационным API.
7. Собрать первую версию дашборда с онбордингом, профилями и мониторингом.
8. Доказать сквозной сценарий M1 на headless Linux и в split-режиме «клиент дома, сервис на VPS».

Следующая практическая веха: **закончить M0 и M1 до написания сложной логики навыков и автономии**.
